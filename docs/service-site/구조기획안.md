# class-site 서비스 사이트 구조 기획안 (초안)

작성: 2026-10-09 · 상태: 교사 검토 전 초안
관련 문서: emq-pack 저장소 `service/기획안.md`(서비스 정의·상품·제작 흐름), `service/모듈_명세.md`(자료팩 모듈)

> **한 줄 요약:** `chuthulhu/class-site`를 **교사 대상 탐구 웹앱 모듈형 제작 서비스의 사이트 저장소**로 바꾼다. 학생용 웹앱(emq-pack, 수행평가 활동들)은 **예시 산출물**로 전시한다. 지금 운영 중인 수업 사이트는 깨지 않고 옆에 둔 채 단계적으로 옮긴다.

## 0. 결론 먼저

| 질문 | 결정(제안) |
|---|---|
| 이 저장소의 역할 | ① 교사 대상 **서비스 사이트** ② **예시 산출물 전시장**(학생용 웹앱 데모) ③ 교사 본인의 **수업 운영 사이트**(기존 기능 유지) |
| 폴더 구조 | `apps/`(배포 단위 3개) + `packages/`(공용 모듈) + `docs/` + `scripts/`·`tests/` |
| 배포 | Cloudflare Pages 프로젝트를 **앱마다 하나씩** 둔다(같은 저장소, 루트 폴더만 다르게) |
| 학생 정보 | 서비스 사이트에는 **학생 정보가 들어오지 않는다.** 예시 산출물 데모는 제출 기능을 끈다 |
| 먼저 할 일 | **보안 정리(0단계)**: 공개 저장소에 들어 있는 제출 키·관리자 암호 기본값을 교체하고 코드에서 뺀다 |
| 이전 방식 | 운영 중인 경로(`/science-experiments/…`, `/physics2/…`)는 유지하고, 새 서비스 사이트는 **새 폴더·새 주소**로 시작한다 |

## 1. 역할 다시 정하기

```
            ┌──────────────────────────────────────────┐
            │  class-site 저장소 (서비스 사이트 저장소)  │
            └──────────────────────────────────────────┘
   교사(고객)가 보는 곳            예시로 보여 주는 곳          선생님 본인 수업
 ┌───────────────────┐      ┌───────────────────┐      ┌───────────────────┐
 │ apps/studio       │ ───▶ │ apps/showcase     │      │ apps/classroom    │
 │ 서비스 사이트      │ 사례 │ 예시 산출물 데모   │      │ 수업 운영(기존)    │
 │ 홈·사례·모듈·의뢰  │      │ 제출 끔·예시 데이터 │      │ 실제 학생 제출     │
 │ 교사 작업실        │      └───────────────────┘      └───────────────────┘
 └───────────────────┘               ▲                          │
          │                          │ 같은 모듈로 만든 결과물     │ 학생 제출
          ▼                          │                          ▼
   의뢰·승인 기록(DB)        emq-pack 저장소(자료팩형 예시)   제출 서버(pdf.physichu.kr)
```

- **예시 산출물**은 두 계열이다.
  - **자료팩 탐구형**: emq-pack(반개방형 탐구 틀, 실제 공공 자료, 분석 도구, 탐구 노트 PDF). 서버 없이 동작.
  - **활동 허브형**: 이 저장소의 수행평가 활동들(활동 안내 → 단계별 작성 → 미리보기 → 제출). 교사 클라우드 자동 제출을 선택할 수 있음.
- 서비스는 두 계열의 모듈을 섞어 주문 제작한다(§6).

### 2-2. 문제점

| # | 문제 | 왜 문제인가 | 처리 단계 |
|---|---|---|---|
| P1 | **공개 저장소에 비밀값이 들어 있음**: 제출 키가 클라이언트 코드(`suhaeng4/index.html`, `modules/hub-config.js`)에 그대로 있고, 관리자 암호 기본값이 `index.html`의 로컬 대체 코드와 `env.example`에 있음 | 누구나 제출 API를 부를 수 있고, 운영 암호가 기본값과 같다면 포털이 열린다. 서비스 사이트로 공개하면 노출이 커진다 | **0단계(즉시)** |
| P2 | `functions/api/proxy.js`가 모든 출처(CORS `*`)에서 외부 API(Graph·Google·Dropbox·Slack 웹훅)로 요청을 중계 | 남용될 수 있는 중계 서버 | 0단계(쓰지 않으면 삭제) |
| P3 | `submit`이 CORS `*`와 `Allow-Credentials`를 함께 둠 | 허용 출처를 수업 주소로 좁혀야 함 | 0단계 |
| P4 | 운영 설정(공개 시각·잠금 기간)이 코드에 날짜로 박혀 있음 | 학기마다 코드를 고쳐야 함 | 3단계(설정 파일로) |
| P5 | 활동마다 큰 단일 HTML(1,200~2,760줄), 공용 모듈은 일부만 사용 | 주문 제작에 재사용하기 어려움 | 5단계(packages로) |
| P6 | 문서가 실제 구조와 다름, 백업이 저장소의 대부분 | 새로 보는 사람(사람·AI)이 길을 잃음 | 1단계 |
| P7 | 학생 학번·이름과 보고서가 교사 OneDrive로 전송됨 | emq-pack의 "학생 정보 비수집" 원칙과 다름. 서비스 상품에서는 **선택 모듈 + 안내·동의**로 분리해야 함 | 설계 원칙(§3) |

> P1은 기획 문서와 별개로 **지금 운영에도 해당되는 위험**이다. 0단계는 교사 승인 후 바로 진행하길 권한다(키 교체는 Cloudflare·제출 서버 환경변수에서 선생님이 직접 해야 하는 부분이 있다).

## 3. 설계 원칙

1. **운영을 깨지 않는다.** 학생이 쓰는 주소와 경로는 학기 중에 바꾸지 않는다. 옮길 때는 방학에, 옛 주소에서 새 주소로 넘겨 준다.
2. **사이트와 학생 앱을 나눈다.** 서비스 사이트(교사용)에는 학생 정보가 들어오지 않는다. 서버(로그인·의뢰 저장)는 교사 정보만 다룬다.
3. **예시 산출물은 데모 모드로 전시한다.** 제출 끔, 예시 데이터, 날짜 잠금 해제. 실제 제출 주소를 부르지 않는다.
4. **공개 저장소에는 비밀값·학생 자료·의뢰 교사 자료를 두지 않는다.** 비밀값은 호스팅 환경변수에만, 의뢰 자료는 저장소 밖(DB·저장소 서비스)에만 둔다. 주문 제작 산출물의 원본은 주문별 비공개 저장소에 둔다.
5. **이식성.** 결과물은 정적 파일 위주, 상대 경로, 호스팅 전용 파일은 앱 폴더 안 한곳에. 특정 호스팅 기능에 핵심을 묶지 않는다(emq-pack AGENTS.md §5와 같은 규칙).
6. **AI가 길을 잃지 않는 저장소.** 루트에 `AGENTS.md`(편집 규칙)와 `CLAUDE.md`(AGENTS.md를 가리킴)를 두고, 앱마다 README를 둔다.

│  └─ classroom/                     선생님 본인 수업 운영 (지금의 class-site/ 폴더)
│     ├─ index.html                  교사 포털

│  ├─ classroom/                     수업 운영 문서(옛 README·PLANNING·ai.md 정리본)

- `BACKUPS/`는 **저장소에서 뺀다.** 지우기 전에 `archive/2025-backups` 같은 태그(또는 브랜치)를 남겨 언제든 되살릴 수 있게 한다.
- `.phase1`·`.backup` 같은 백업 파일, 루트의 옛 의존성(`package.json`의 Express·Puppeteer는 제출 서버용)도 정리한다. 제출 서버 코드는 **별도 비공개 저장소**로(토큰 파일을 다루므로).

### 4-1. 폴더별 역할과 규칙

| 폴더 | 누가 보나 | 학생 정보 | 서버 | 배포 |
|---|---|---|---|---|
| `apps/studio` | 의뢰 교사·방문자 | 없음 | 있음(의뢰·교사 계정만) | Pages 프로젝트 A |
| `apps/showcase` | 방문 교사 | 없음(데모 모드) | 없음 | Pages 프로젝트 B 또는 A의 하위 경로 |
| `apps/classroom` | 선생님 학급 학생 | 있음(제출 시 학번·이름) | 있음(제출) | Pages 프로젝트 C(지금의 프로젝트) |
| `packages/*` | 제작자·Claude | — | — | 빌드 때 각 앱에 복사 |

Cloudflare Pages는 프로젝트마다 **루트 폴더**를 정할 수 있고 서버 함수(`functions/`)는 그 루트 안에 있어야 하므로, 앱마다 `functions/`를 따로 둔다.

## 6. 모듈 체계 (두 계열 합치기)

| 층 | 자료팩 탐구형(emq-pack) | 활동 허브형(class-site) | 서비스에서 부르는 이름 |
|---|---|---|---|
| 안내·읽기 | 현상 카드, 개념 연결, 낱말 풀이 | 문제 상황 읽기(`suhaeng3`), 인터랙티브 읽기 자료(`suhaeng1`), 단계 안내(`suhaeng2`·`guide`) | **안내 모듈** |
| 탐구 구조 | 반개방형 탐구 틀(【빈칸】), 1부 탐색 활동, 추천 자료 조합 | 단계형 작성 탭, 차시 구분(`session1`·`session2`) | **탐구 구조 모듈** |
| 근거 | 자료 카드(성격·읽는 법·출처), 실제 공공 자료 | 출처 입력 양식(논문·도서·잡지·URL, `SOURCE_TYPES`) | **근거 모듈** |
| 분석 | 그래프로 보기, 관계 찾기, 비교 정리표, 전용 뷰어 | (없음) | **분석 도구 모듈** |
| 기록 | 탐구 노트 1부·2부, 초기 설명 잠금, AI 활용 기록 | 자동 저장, 미리보기·보고서 생성(`generateDocHtml`), 사진 압축 첨부 | **기록 모듈** |
| 제출 | PDF 인쇄 + 내보내기 파일(서버 없음) | PDF 서버 변환 → 교사 OneDrive 저장, 인앱 브라우저·iOS 대응 다운로드 | **제출 모듈**(방식 선택) |
| 운영 | 2부 열림·닫힘(`POLICY`), 오프라인 단일 파일 | 공개 시각 잠금, 교사키 우회 | **운영 모듈** |

**제출 방식은 상품에서 고르게 한다.**

| 방식 | 학생 정보 | 서버 | 장점 | 주의 |
|---|---|---|---|---|
| ① PDF 저장 제출(기본) | 학교 밖으로 나가지 않음 | 없음 | 개인정보 걱정 적음, 어디서나 동작 | 교사가 파일을 따로 걷어야 함 |
| ② 교사 클라우드 자동 제출(선택) | 학번·이름·보고서가 **교사 본인 계정**으로 감 | 제출 서버 | 수합 자동, 폴더 자동 분류 | 학교 개인정보 지침 확인, 학생 안내문, 교사 계정 연결(토큰) 관리 |

## 7. emq-pack과의 연결

- emq-pack은 **별도 저장소·별도 주소**(후보 `emq.physichu.kr`)를 유지한다. 이 저장소로 옮기지 않는다(학생 기록이 주소별 브라우저 저장소에 있으므로 주소가 바뀌면 이어지지 않는다).
- 사례 페이지(`apps/studio/cases/emq-pack/`)는 화면 캡처·채점요소 대응 그림·제작 기록 요약을 싣고, 체험은 **emq-pack 데모판 주소**로 연결한다.
  - 데모판은 emq-pack에서 `POLICY.reportOpen = true`로 빌드한 별도 배포(예: `emq-demo.physichu.kr`)로 만든다. emq-pack 쪽 작업이므로 그 저장소에서 승인받아 진행한다.
- 서비스 기획 문서의 원본은 당분간 emq-pack `service/`에 있다. 사이트 제작이 시작되면 이 저장소 `docs/service-site/`로 옮기고 emq-pack 쪽에는 링크만 남긴다.

| 주소(후보) | 무엇 | 앱 |
|---|---|---|

## 9. 서비스 사이트 화면 (apps/studio)

페이지 구성과 의뢰 폼 항목은 emq-pack `service/기획안.md` §6을 따른다. 이 저장소에서 정할 구현 사항만 적는다.

| 페이지 | 경로 | 구현 방식 | 단계 |
|---|---|---|---|
| 홈 | `/` | 정적 HTML | MVP |
| 사례 | `/cases/`, `/cases/<이름>/` | 정적 HTML, 데모 링크 | MVP |
| 제작 과정·상품·원칙·FAQ | `/process/` `/pricing/` `/principles/` `/faq/` | 정적 HTML | MVP |
| 의뢰 폼 | `/request/` + `POST /api/request` | 정적 폼 + 서버 함수(접수 → 저장 → 선생님에게 알림 메일) | MVP |
| 모듈 갤러리 | `/modules/`, `/modules/<id>/` | 정적 HTML + showcase 데모 일부 삽입 | 1차 |
| 교사 작업실 | `/studio/` + `/api/studio/*` | 로그인(이메일 링크 방식 등), 의뢰 단계·승인·수정 요청·산출물 | 파일럿 |

- 기술: 기존과 같이 **프레임워크 없는 HTML·CSS·JS**로 시작한다(Tailwind는 CDN 대신 빌드해서 넣는 방식 권장, 학교망 차단 대비).
- 저장: 의뢰·교사 계정·승인 기록은 DB(후보: Cloudflare D1), 첨부 파일(평가계획서)은 파일 저장소(후보: R2). 저장소 밖에 두고, 보관 기간과 삭제 절차를 원칙 페이지에 공개한다.
- 인증: 지금의 "공용 관리자 암호" 방식은 쓰지 않는다. 교사마다 계정(이메일 확인)을 둔다.
